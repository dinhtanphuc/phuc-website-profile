This guide shows QC engineers how to build a custom GitHub Copilot agent in VS Code that reads Jira tickets through Atlassian MCP, inspects impacted components, pages, selectors, and flows in the repository, then produces evidence-based test cases.

For this delivery variant, publishing to Confluence is the default output. That matters, but it is still a secondary packaging step. The primary responsibility is ticket analysis, code-impact inspection, and testcase generation.

1. Overview

1.1 What this agent solves

Many teams still copy Jira acceptance criteria into spreadsheets or Confluence by hand, then try to infer the impacted UI and flows from memory. That approach is slow and usually drops context. A custom agent can do the heavy lifting earlier in the process.

  • Read the Jira ticket through Atlassian MCP
  • Scan the workspace for impacted pages, selectors, POMs, tests, and helpers
  • Generate an impact assessment backed by repository evidence
  • Produce a structured test case set before any delivery formatting starts
  • Create or update the Confluence page only after the testcase set is complete

1.2 Real-world example

PhucGenerateTestCFpage reads Jira ticket FKBS2-2585 through Atlassian MCP, scans the impacted selectors and pages, prints an impact assessment, generates structured test cases, and then creates or updates a Confluence page in the FKBS testcase area.

That sequencing is the core design decision of this agent: Jira evidence first, testcase generation second, Confluence publishing last.

3. Step by Step: Build the Custom Agent

The design principle behind PhucGenerateTestCFpage.agent.md is straightforward: Jira reading and testcase generation come first; Confluence publishing comes after.

3.1 Create a New Agent File

Agent definitions live in .github/agents/ at the root of the repository. Create a separate file for the Confluence-delivery variant: 

.github/agents/PhucGenerateTestCFpage.agent.md

Keeping this variant separate from a TSV-focused agent avoids mixing delivery rules, page hierarchy constraints, and formatting responsibilities.

3.2 Define the Role: Jira/MCP First, Confluence Second

The role section should state the priority explicitly. The agent exists to turn Jira requirements into evidence-based test cases. Confluence is only how this variant publishes the final output. 

---
description: "Use when QC needs Jira ticket analysis, impacted component/page review, selector inspection, and evidence-based testcase generation with default Confluence delivery via Atlassian MCP."
name: "PhucGenerateTestCFpage"
tools: [read, search, edit, todo, atlassian/*]
---
You are PhucGenerateTestCFpage. Your primary responsibility is to read Jira tickets through Atlassian MCP,
inspect impacted pages, components, selectors, shared flows, POMs, and existing tests in the workspace,
then generate the right structured testcase set.

Confluence publishing is the default delivery path for this variant, but it only happens after testcase
generation is complete.

That wording prevents the agent from over-optimizing for page creation while neglecting impact analysis and testcase quality.

3.3 Declare MCP and Delivery Tools

The agent needs tools for two layers of work: evidence gathering and delivery. In the example above, atlassian/* assumes the Atlassian MCP server is registered with the server alias atlassian.

  • read and search for repository inspection
  • todo for multi-step testcase generation workflow
  • edit when the user also asks for a local TSV or artifact output
  • atlassian/* for Jira ticket reading and Confluence create, update, or move actions

Listing tools by name keeps the agent anchored to the right MCP surface instead of drifting into generic chat-only behavior.

3.4 Set the Default Destination for This Variant

This section is only about where the finished testcase set should land when Confluence is the selected output. Define a predictable title pattern, parent area, and hierarchy rule.

Recommended defaults

  • Destination space: FKBS testcase area
  • Template page: 3553951820
  • Hierarchy rule: create new pages as siblings of the template page
  • Title pattern: [Ticket Key] - [Short Requirement] - Test Cases

3.5 Design the Workflow With Testcase Generation First

The workflow should make the sequencing explicit so Confluence packaging never jumps ahead of analysis. 

## Workflow
1. Read the Jira ticket and linked context through Atlassian MCP.
2. Inspect impacted components, selectors, pages, shared flows, tests, and helpers in the workspace.
3. Produce an impact assessment with evidence.
4. Generate structured test cases.
5. Search Confluence for an existing page for the ticket.
6. Update the existing page when appropriate; otherwise create a new page.
7. Publish Confluence output only after testcase generation is complete.
8. Export TSV only when the user explicitly asks for it.

Step 7 is what keeps the delivery mode honest. Packaging is downstream of testcase design, not a substitute for it.

3.6 Add Confluence Packaging Rules, Delivery Mode, and Constraints

Confluence rules still matter, but they govern how the generated testcase set is packaged, not how it is designed.

Rule Why it matters
Page naming convention Makes ticket-to-page traceability obvious
Template reuse required Keeps layout consistent with the FKBS team standard and reuses page 3553951820
Page width and readability Helps wide testcase tables stay usable even when full-width cannot be set by API
Test case content rules Ensures each case still includes preconditions, steps, expected results, and evidence notes
Duplicate avoidance Searches Confluence before publishing so the agent updates the right page instead of creating clutter

The delivery hierarchy should be stated directly: testcase generation is the primary outcome; Confluence publication is the default delivery mode; TSV is secondary and only produced when requested. 

## Critical Constraints
- Do not publish before testcase generation is complete.
- Do not invent selectors, components, flows, or coverage not found in Jira or the repository.
- Always show an impact assessment before finalizing the testcase set.
- Reuse template page 3553951820 for structure.
- Search for an existing Confluence page before creating a new one.
- Keep new pages as siblings of the template page.
- Treat TSV as optional secondary output, not the default.

3.7 Commit and Share

After validating the guide and agent together, commit the new agent file so the workflow becomes available to the rest of the team. 

git add .github/agents/PhucGenerateTestCFpage.agent.md
git commit -m "Add Confluence delivery testcase generation agent"

4. How to Use the Agent

4.1 Invoking the Agent

  1. Open Copilot Chat.
  2. Switch to Agent mode.
  3. Select PhucGenerateTestCFpage.
  4. Ask for ticket analysis and testcase generation.

4.2 Example Prompts

Prompt What happens
Analyze FKBS2-2585 and generate test cases Reads the Jira ticket via Atlassian MCP, scans the codebase, generates the testcase set, then publishes it to Confluence by default
Generate test cases for FKBS2-2500 Runs evidence gathering, impact assessment, and testcase generation with Confluence delivery as the default output
Update the test cases for FKBS2-2500 Searches Confluence first and updates the existing page instead of creating a duplicate
Analyze FKBS2-2585 and also export TSV Publishes the Confluence page and creates a local TSV artifact as secondary output

4.3 What the Agent Does

  1. Reads Jira requirements, acceptance criteria, linked pages, and ticket context via Atlassian MCP.
  2. Searches the repository for impacted UI components, selectors, POMs, tests, and shared flows.
  3. Builds an impact assessment that explains what changed and why each testcase exists.
  4. Generates a structured testcase set with preconditions, steps, expected results, and evidence notes.
  5. Searches Confluence for an existing page, then updates or creates the page in the FKBS hierarchy.

6. Benefits

Benefit Explanation
Automated Jira-to-testcase flow The agent reads the ticket and turns it into a structured testcase set without manual rewriting.
Evidence-based impact coverage Selectors, pages, shared flows, and existing tests can be inspected before the cases are generated.
Consistent team delivery For this variant, the final testcase set is published into the existing Confluence structure instead of living only in chat.

7. Limitations and Considerations

Limitation Mitigation
AI can still hallucinate Always review the generated testcase set before execution.
Confluence page width via API Page width may still default to fixed width, so manual full-width adjustment can be needed after publishing.
MCP setup required Each machine needs Atlassian MCP configured correctly for both Jira and Confluence.
Large ticket context Very large tickets or broad refactors may need to be split into smaller generation requests.
Not a replacement for QC judgment The agent accelerates testcase design but does not replace exploratory thinking or product knowledge.

8. Advanced Tips

8.1 MCP Server Configuration

A common setup is to register an Atlassian MCP server in .vscode/mcp.json and expose both Jira and Confluence capabilities through the same server alias. The exact package name and environment variables depend on the Atlassian MCP server implementation your team chose. 

{
  "servers": {
    "atlassian": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "your-atlassian-mcp-package"],
      "env": {
        "ATLASSIAN_BASE_URL": "https://your-company.atlassian.net",
        "ATLASSIAN_USER_EMAIL": "qa-team@example.com",
        "ATLASSIAN_API_TOKEN": "${input:atlassianApiToken}"
      }
    }
  }
}

Once the server alias is in place, the agent can reference it with tools: [atlassian/*] in the frontmatter.

8.2 Iterate After Real Usage

After 3 to 5 real tickets, review the agent's output. If the same issue keeps showing up, refine the guide or add a precise new constraint rather than piling on generic instructions.

8.3 Keep Delivery and Design Separate

If QC feedback says the Confluence page structure looks fine but testcase scope is weak, improve the Jira-reading, impact-analysis, and testcase rules first. Do not over-focus on delivery formatting when the real problem is test design quality.
