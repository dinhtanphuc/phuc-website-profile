1. Overview

In automated testing, accurately identifying UI elements is a core part of building stable and maintainable test cases. This guide provides detailed guidelines on how to capture elements effectively, including common locator analysis, practical selector selection rules, and maintainable ways to organize selectors in large projects.

The goal is to improve reliability and maintainability across frameworks such as Selenium WebDriver, Cypress, or Playwright. In this article, the examples use Cypress, with special attention to projects where the application itself uses C# on the backend or server-rendered UI side.

Important context: even in projects built with ASP.NET, Razor, Blazor, or other C# stacks, Cypress tests are still written in JavaScript or TypeScript.

What changes is the DOM you receive from that application, along with the kinds of dynamic IDs, form attributes, and rendering patterns that your selectors need to handle well.

By following these practices, teams can define a consistent locator strategy, choose stable selectors, organize locators with maintainable patterns such as the Page Object Model, and avoid common pitfalls in dynamic or complex DOM structures.

2. How It Works

Cypress officially recommends selecting elements in ways that reflect stable intent rather than styling or DOM position. The best starting point is the Cypress best practices guide: Best Practices - Selecting Elements.

Consider this button that we want to interact with: 

<button
  id="main"
  class="btn btn-large"
  name="submission"
  role="button"
  data-cy="submit"
>
  Submit
</button>

Several locator options are available, but they are not equally stable. The rest of this guide shows how to prioritize selectors from most durable to most fragile.

3. Prioritize Stable and Semantic Selectors

3.1 Using data-* Attributes: the Gold Standard

Introduce dedicated attributes such as data-cy, data-testid, or data-qa specifically for testing. These are usually the most stable option because they are not tied to styling, layout, or displayed copy.

  • Stability: less likely to change because of CSS or UI refactoring
  • Clarity: makes test intent obvious to anyone reading the DOM
  • Team collaboration: frontend and C# developers can preserve these attributes as part of the test contract
<button data-cy="submit">Submit</button>

cy.get('[data-cy="submit"]').click();

3.2 Use Unique and Static IDs

If an element has an ID that is unique and stable across the entire DOM, it is a strong selector choice. Cypress can query IDs efficiently and the intent stays clear. 

<button id="mainSubmit">Submit</button>
<input type="text" id="emailInput" placeholder="Enter email">

it('Interact with elements by ID', () => {
  cy.visit('/page.html');
  cy.get('#mainSubmit').click();
  cy.get('#emailInput').type('test@example.com');
});

This works well when the ID is intentionally designed, not framework-generated.

3.3 Avoid Dynamic IDs

Dynamic IDs are generated values that change across page loads, sessions, environments, or builds. They are common in older ASP.NET Web Forms pages and in modern component libraries. 

<input id="ctl00_MainContent_txtEmail" />
<div id="react-select-12-option-3"></div>

cy.get('#ctl00_MainContent_btnSubmit').click();
cy.get('#react-select-12-option-3').click();

Why this is risky: dynamic IDs create tests that pass today and fail after the next render, deployment, or library upgrade.

3.4 Use name or formControlName for Form Elements

In forms, name and Angular's formControlName often reflect data binding rather than presentation. That makes them useful in applications where a C# backend depends on predictable form field names. 

<input type="email" name="userEmail" placeholder="Enter your email">

it('Types email using the name attribute', () => {
  cy.visit('/page.html');
  cy.get('[name="userEmail"]').type('test@example.com');
});

3.5 Use placeholder, aria-label, or title Only When Necessary

These attributes can be useful when no better selector is available. They carry semantic meaning and help accessibility, but they should usually be considered fallback selectors rather than the first choice. 

<input type="text" placeholder="Search">

it('Types into the search input using the placeholder', () => {
  cy.visit('/page.html');
  cy.get('[placeholder="Search"]').type('keyword');
});

These are still preferable to brittle positional selectors, but they can change when content or accessibility wording changes.

3.6 Use Content-Based Selectors with cy.contains()

cy.contains() is useful when text itself is the user-facing contract. It is much better than inventing a complex CSS chain just to locate a button with stable visible text. 

cy.contains('Submit').click();
cy.contains('button', 'Cancel').click();
cy.contains('div.error', 'Invalid username or password').should('be.visible');

Prefer the variant with both selector and text when you want to reduce ambiguity.

3.7 Use CSS Class Selectors Carefully

If a single semantic class is not enough, combine stable classes or scope within a stable parent container. The point is to express structure without depending on fragile visual wrappers. 

<button class="button primary">Submit</button>
<div class="product-card">
  <div class="info">
    <h2 class="title">Product Name</h2>
  </div>
</div>
<div class="mat-select-search-inner">
  <input
    type="text"
    class="mat-select-search-input"
    placeholder="Search..."
    aria-label="Search Country Code"
  />
</div>

cy.get('.button.primary');
cy.get('.product-card .info .title');
cy.get('.mat-select-search-inner > .mat-select-search-input').type('NO');

Use this approach only when the classes are intentionally meaningful and likely to remain together.

3.8 XPath and Positional Selectors Should Be the Last Resort

XPath can express complex DOM traversal, but Cypress does not support it natively. You need an additional plugin to use it, and XPath expressions often become hard to read and expensive to maintain.

Similarly, selectors based on :nth-child, index positions, or deep DOM order tend to break whenever the UI layout changes.

Use only when there is no cleaner contract.

If you think XPath is required, first check whether a stable data-* attribute, form attribute, container scope, or cy.contains() can solve the problem more clearly.

4. Master DOM Traversal in Cypress

Sometimes the best strategy is not a more complicated root selector, but better scoping from a stable parent. Cypress gives you traversal helpers for that.

4.1 Parent and Children

cy.get('.child-element').parent('.parent-container').should('exist');

cy.get('.parent-element').children().should('have.length', 3);
cy.get('.parent-element').children('.specific-child').should('be.visible');

4.2 Other Useful Traversal Commands

cy.get('.main-container').find('.nested-element').click();

cy.get('.form').within(() => {
  cy.get('input[name="username"]').type('testuser');
  cy.get('input[name="password"]').type('password');
  cy.get('button[type="submit"]').click();
});

cy.get('.row-item').siblings().should('have.length.greaterThan', 0);
cy.get('.current-step').next().should('be.visible');
cy.get('.current-step').prev().should('be.visible');

The most maintainable version usually starts from one stable container and narrows the search within that boundary.

5. Managing Selectors in Large Projects

5.1 Use the Page Object Model

Encapsulate selectors and page actions into reusable objects. This keeps tests readable and isolates selector changes. 

class LoginPage {
  elements = {
    usernameInput: () => cy.get('[data-cy=username]'),
    passwordInput: () => cy.get('[data-cy=password]'),
    loginButton: () => cy.get('[data-cy=login-button]')
  };

  login(username, password) {
    this.elements.usernameInput().type(username);
    this.elements.passwordInput().type(password);
    this.elements.loginButton().click();
  }
}

export default new LoginPage();
import loginPage from '../support/pages/LoginPage';

describe('Login', () => {
  it('should log in successfully', () => {
    loginPage.login('admin', 'password123');
  });
});

5.2 Centralize Selectors with a Selectors File

If full page objects feel too heavy, a centralized selectors module still improves consistency and reduces duplication. 

export const NO_ODFSelectors = {
  ODF_InputWP: '[formcontrolname="popWpId"]',
  ODF_InputWP_option: '.mat-option-text',
  ODF1_Cabinet: '[formcontrolname="odf1Cabinet"]',
  ODF1_Tray: '[formcontrolname="odf1Tray"]',
  ODF1_Position: '[formcontrolname="odf1Position"]',
  ODF1_Damping: '[formcontrolname="odf1Damping"]',
  ODF_Submit: 'Opslaan'
};
it('should show error when ODF1_Cabinet is not filled', () => {
  cy.contains(NOSelectors.NOpage).click();
  cy.url().should('include', '/aansluiting');
  cy.get(NOSelectors.connectionDetailButton).click();
  cy.get(NOSelectors.DOTicon).click();
  cy.get(NOSelectors.DOTpopup).should('be.visible');
  cy.contains(NOSelectors.ODFoption).click();
  cy.get(NO_ODFSelectors.ODF1_Tray).type(ODF.Tray_1);
  cy.get(NO_ODFSelectors.ODF1_Position).type(ODF.Position_1);
  cy.contains(NO_ODFSelectors.ODF_Submit).click();
  cy.contains('Technische ODF data is incompleet.').should('be.visible');
});

5.3 Store Selectors in CSV and Generate Page Objects

For large teams, a CSV file can become a source of truth for selectors. Copilot can then help generate or update page objects from that list. 

Page,Element,Selector
LoginPage,Username Input,#username
LoginPage,Password Input,#txtPassword
LoginPage,Login Button,[data-cy="login-button"]
LoginPage,Error Message,.error-message
class LoginPage {
  visit() {
    cy.visit('https://portal.fk-bs-staging.infodation.vn/');
  }

  login(username, password) {
    cy.get('#username').type(username);
    cy.get('#txtPassword').type(password);
    cy.get('[data-cy="login-button"]').click();
  }

  getErrorMessage() {
    return cy.get('.error-message');
  }
}

export default LoginPage;
import LoginPage from '../pages/LoginPage';

describe('Login Tests', () => {
  const loginPage = new LoginPage();

  beforeEach(() => {
    cy.viewport(1900, 920);
    loginPage.visit();
  });

  it('should login successfully with valid credentials', () => {
    cy.fixture('user').then((user) => {
      loginPage.login(user.valid.username, user.valid.password);
      cy.url().should('include', '/home?tab=Sales');
    });
  });
});

5.4 Encapsulate Common Actions in Custom Commands

For repeated business actions such as logging in, custom commands reduce noise inside test cases. 

Cypress.Commands.add('login', (username, password) => {
  cy.get('[data-cy=username]').type(username);
  cy.get('[data-cy=password]').type(password);
  cy.get('[data-cy=login-button]').click();
});

6. Conclusion: Selector Priority in Cypress

Choosing the right selector is critical for reliability, readability, and long-term maintainability. The following priority table is a practical summary from best to worst.

Priority Selector Type Stability Readability Maintainability Main advantages
1 data-cy, data-testid Very high High Very high Designed specifically for testing and minimally affected by UI styling changes
2 Static id High High High Fast and unambiguous when the ID is intentionally stable
3 name, formControlName Medium high Medium Medium high Useful for form workflows and often aligned with data binding
4 placeholder, aria-*, title Medium Medium Medium Semantic fallback when stronger contracts are unavailable
5 cy.contains() Medium Medium Medium Useful when visible text is the stable contract and ambiguity is controlled
6 Dynamic id Very low Medium Low Looks precise, but breaks easily when frameworks regenerate values
7 Class chains and nth-child Low Low Low Should be used only when classes are intentionally stable and no better contract exists
8 XPath Low Low Low Powerful for complex traversal, but not native in Cypress and costly to maintain

The practical rule is simple: prefer selectors that describe business intent, not visual implementation details. That single decision reduces flaky tests, lowers maintenance cost, and makes your automation suite easier to scale.
